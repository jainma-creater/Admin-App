5. IMPORTANT STORAGE DECISION
============================================================

DO NOT use PostgreSQL as the primary long-term storage location for original
photo binaries.

PostgreSQL must store:

- photo ID
- visit ID
- asset ID
- object storage key
- filename
- MIME type
- dimensions
- file size
- checksum
- thumbnail reference
- OCR status
- OCR result
- created timestamp
- uploader
- upload status
- metadata

Object storage must store the actual images.

Use an S3-compatible abstraction.

Production options:

- AWS S3
OR
- MinIO on company infrastructure

The application must not be tightly coupled to one provider.

Create a storage service interface such as:

StorageService

with operations:

- upload()
- download()
- delete()
- exists()
- generate_presigned_url()
- generate_thumbnail()
- get_metadata()

The backend must communicate with the abstraction rather than directly
embedding S3/MinIO-specific logic throughout the application.

DO NOT introduce Kubernetes unless there is a real requirement.

DO NOT introduce dozens of microservices.

DO NOT introduce Kafka unless there is a demonstrated requirement.

DO NOT introduce unnecessary cloud services.

- modular monolith FastAPI
- one worker service
- PostgreSQL
- Redis
- object storage
- Next.js
- Expo/React Native
- nginx/Cloudflare

This is sufficient for the expected scale.
